# Plan: move Workiya from SQL Server to PostgreSQL (Neon)

Status: **draft for review**. Branch `db/WI-TBD/postgres-migration`, worktree `D:\Project\Workiya-postgres`.

## Goal

Workiya gets its **own** PostgreSQL 18 database on Neon (`WorKiya`, AWS Singapore) with PostGIS
available. Nothing is shared with the other system any more. The REST API and the frontend keep
working exactly as today; only the database layer changes. SQL Server (`dbTest_VSE`) is only
**read** during the one-time data copy and is never changed, so it stays as the fallback.

tables (Tenants, UserRoles, UserConfigs, UserType, SniffTest, SniffJoin).
The `Legacy*Id` columns are dropped, because the tables they point to are not moved.

## Design decisions (need your OK)

1. **PostgreSQL naming: `snake_case`** for tables and columns (`company_id`, `created_at`), the
   standard in PostgreSQL (no quoting). **The API does not change**: new endpoints already map
   rows to camelCase DTOs, and the older Users / Employees / Managers / Companies endpoints alias
   their columns back to the same PascalCase names the frontend reads today.
2. **Driver: `pg` (node-postgres)** plus a small helper so repository SQL keeps readable named
   parameters: `db.query("... WHERE id = @id", { id })` becomes `$1` safely under the hood.
   Every query stays parameterised. Prisma / Drizzle were considered; they would mean rewriting
   every repository in a new style and are not needed for this move.
3. **Types:** `datetimeoffset`/`datetime2` → `timestamptz` (all UTC); `nvarchar(n)` → `varchar(n)`;
   `bit` → `boolean`; JSON text → **`jsonb`** (validated by the database, queryable);
   `uniqueidentifier` → `uuid`; emails → **`citext`** (case-insensitive); ids →
   `integer GENERATED BY DEFAULT AS IDENTITY` (existing ids are kept, sequences reset after copy).
4. **Change history** (SQL Server temporal tables have no built-in PostgreSQL equivalent):
   one shared trigger function writes the old row into `accounts_history`,
   `account_assignments_history`, `activities_history`, `submissions_history` on every UPDATE /
   DELETE, with `valid_from` / `valid_to`. Same behaviour as today.
5. **Audit log immutability gets stronger:** triggers block UPDATE, DELETE **and TRUNCATE**
   (SQL Server could not block TRUNCATE), and the app's database role gets INSERT/SELECT only.
6. **Stronger tenant rules now that `users` is ours:** foreign keys `users.company_id →
   companies` and `(company_id, id)` keys, so an activity can only be assigned to a user of the
   same company **in the database itself** (today only the API checks this).
7. **Passwords:** the shared-table restriction is gone, so login will upgrade old PBKDF2 hashes to
   **Argon2id** automatically, and new or reset passwords use Argon2id directly.
8. **Old inline SQL in controllers** (users, employees, managers, companies) moves into
   repositories while it is rewritten anyway (controllers keep only HTTP handling).
9. **Real database tests:** keep the fast mocked unit tests, and add integration tests that run
   every repository against a real PostgreSQL (GitHub Actions service container with PostGIS;
   locally a Neon branch). This catches SQL mistakes that mocks cannot.

## SQL Server → PostgreSQL rewrites (91 queries in 17 files)

| SQL Server | PostgreSQL |
|---|---|
| `GETUTCDATE()`, `SYSDATETIMEOFFSET()` | `now()` |
| `TOP 1` | `LIMIT 1` |
| `OFFSET … ROWS FETCH NEXT … ROWS ONLY` | `LIMIT … OFFSET …` |
| `OUTPUT inserted.*` | `RETURNING *` |
| `OUTER APPLY` | `LEFT JOIN LATERAL` |
| `WITH (UPDLOCK, HOLDLOCK)` | `SELECT … FOR UPDATE` |
| `ISJSON()` checks | `jsonb` column type |
| filtered unique index `WHERE IsDeleted = 0` | partial unique index (same idea) |
| duplicate-key errors 2601 / 2627 | SQLSTATE `23505` |
| `sql.Transaction` / `request.input()` | `pg` client `BEGIN/COMMIT` + helper params |

## Steps

1. **Schema migrations** in `backend/db/postgres/` (`YYYYMMDDHHMMSS_<id>_<desc>.sql`, UP/DOWN).
   PostgreSQL runs DDL inside transactions, so a failed migration rolls back completely.
   The runner is adapted from today's one (still prints what it did, still needs `--yes`).
2. **Data copy script** `backend/scripts/copy-sqlserver-to-postgres.js`: reads SQL Server
   (read-only), writes Neon in foreign-key order inside **one transaction**, converts types
   (JSON text → jsonb, bit → boolean, offsets → UTC), keeps ids, resets sequences, then
   **verifies row counts and key columns per table** and rolls back on any mismatch.
   Has a dry-run mode that only reports what it would copy.
3. **Backend switch:** new `config/db.js` on `pg` (pool for the app on `DATABASE_URL`,
   direct connection for migrations on `DATABASE_URL_DIRECT`, TLS `verify-full`); rewrite the
   17 files; `MSSQL_*` settings and the `mssql` package removed; old `migrate.js` replaced by a
   seed script for a first Super Admin (password from an environment variable, not hard-coded).
4. **Tests:** update mocks and SQL assertions; add the real-PostgreSQL integration suite; CI gets
   a PostGIS service. Coverage gates stay (80% overall, 95% auth).
5. **Run on Neon:** apply migrations, copy data (dry run first, then real), verify counts.
6. **You test in the browser** against Neon: login with existing passwords, accounts, assign reps,
   activities, report + approve, settings, users / password reset.
7. Commit, then ask before merging into `development` and pushing.

## Rollback

SQL Server is never written to. If anything is wrong after the switch: point `.env` back to the
old values and run the `development` branch as before. On Neon, migrations have DOWN sections,
and the whole database can also be reset from a Neon branch / point-in-time restore.

## Effort

About 1.5–2 weeks for one developer; with a multi-agent workflow a few days of build time plus
your testing. Frontend: no changes expected.
